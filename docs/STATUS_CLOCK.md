# Clock synchronization through GET_STATUS

See ../../Lora_remote/docs/RTC_TIME.md for the full UI/startup flow and bench log.

Remote now requests unicast GET_STATUS after its startup and after saving its
clock. Existing payload module=0, syncTime=civil calendar encoded as Unix-like
seconds. No new LoRa opcode or wire-layout change is required.

Motor_SyncStatusTime ignores times before 2024 or after 2099. It refreshes the
slave RTC, compares the existing 30-second tolerance and updates a differing
clock even while ON. During an active ON timer it preserves remaining seconds
by rebasing the deadline; already expired timers stay due. The clock/deadline/
status cache update is protected from scheduler-task preemption with IRQs still
enabled. No power action or new history event is generated by time sync itself;
old history timestamps are immutable. SET_SCHEDULE still uses its own received
absolute deadline and does not use the status-sync rebasing path.

USB TIME is read-only. Reply contains TS, DATE, CLOCK, DEADLINE and PWR. The
reply uses the live system-task cache; no PC or USB setter runs on the slave.

Deployment 2026-11-19: standalone app at 08000000, 44240 bytes, CRC B6AFF1B5;
ST-Link verified, sectors 0..43 only, history/config preserved. Configuration
backup hash matched before/after (backups/date-time-20261119/). Motor was set OFF
before programming and remained OFF. Startup and UI-save propagation were
verified physically against remote; ON countdown preservation and error cases
were checked in ARM emulation (tools/test_status_clock.py).
